# DXCEL DB·API 설계

상태: 핵심 스키마·RLS·DB RPC를 migration으로 구현했다. 구체적인 계약과 검증 범위는 [DB 구현 현황](database-implementation.md)을 따른다. HTTP 수집 API와 프론트 연결은 후속 작업이다.

## 원칙

- Postgres UUID 식별자와 UTC 시각을 사용한다.
- 프로젝트 소속 데이터에 project_id를 두고 복합 FK로 프로젝트 간 참조를 차단한다.
- 실행 결과는 추가 방식으로 보존한다. 정정·재평가는 새 기록과 이전 기록 참조로 연결한다.
- 설계·노트·baseline을 버전으로 관리한다.
- 유연한 설정은 jsonb, 정렬·집계할 스칼라 지표는 별도 행으로 저장한다.
- 개인별 데이터, 실제 인증 정보, 원본 데이터 행은 저장 규약에서 제외한다.
- 실수 삭제를 막기 위해 연구 기록의 cascade delete를 피하고 보관 상태를 사용한다.

## 테이블

| 테이블 | 주요 정보 |
| --- | --- |
| projects | 프로젝트 식별자, 이름, 보관 상태 |
| project_members | 구성원과 owner/editor/viewer 역할 |
| experiments | 실험 번호, 담당자, 이전 실험, 현재 설계·대표 결과 |
| experiment_revisions | 가설, 변경 이유, 평가 계획의 버전 |
| comparison_contexts | 데이터셋·분할·평가 방법·지표 정의·평가량 |
| metric_definitions | 지표 이름, 버전, 단위, 개선 방향 |
| context_metrics | 비교 조건별 지표와 필수 여부 |
| run_groups | 동일 비교 조건의 반복 묶음과 확정 상태 |
| generation_outputs | 생성 결과의 논리 식별자와 fingerprint |
| runs | 개별 평가 결과, 반복 식별자, attempt, 상태, 설정, 이전 평가 참조 |
| run_metrics | 실행별 스칼라 값, 결측·오류 상태 |
| run_group_selections | 확정 비교에 포함된 실제 평가 참조 |
| run_group_exclusions | 제외된 반복과 그 이유 |
| baseline_versions | 내부 결과 또는 출처가 있는 보고값의 버전 |
| baseline_reported_metrics | 보고된 수치와 알려진 표준편차·표본 수 |
| notes | 실험 또는 개별 실행에 연결된 노트 |
| note_revisions | 노트 본문의 수정 이력 |
| ingestion_tokens | 프로젝트 범위 등록 권한의 해시·만료·폐기 정보 |
| audit_events | 변경 주체·대상·시각·이유 |

위 19개 테이블을 구현했다. 등록 토큰은 해시·만료·폐기 메타데이터 저장 구조만 있으며, 발급·인증 endpoint는 아직 없다.

## 참조와 불변 조건

- 실험 번호는 프로젝트 안에서 유일하며 생성 후 변경하지 않는다.
- 설계 revision은 해당 실험에 속해야 한다.
- 실행별 등록 ID는 프로젝트 안에서 유일해야 한다.
- 같은 반복의 재시도는 새로운 ID와 attempt를 사용한다.
- 결과의 지표 정의는 실행 묶음의 comparison context에 속해야 한다.
- 확정 묶음의 선택·제외 목록은 예상 반복을 중복 없이 모두 설명해야 한다.
- 동일 생성 결과의 복수 평가를 서로 다른 독립 반복으로 세지 않는다.
- 비교 묶음 확정 후에는 포함 기록을 변경하지 않는다.
- 일부 반복만 같은 조건으로 재평가한 경우 새 묶음이 기존 평가를 참조할 수 있다.
- 다른 평가 방법이나 설정의 결과는 같은 확정 묶음에 섞지 않는다.
- baseline과 대표 결과는 확정된 결과를 참조한다. 교체 이유와 당시 기준을 보존한다.
- 비교 조건이 불명확한 보고값은 참고용으로만 표시한다.
- 노트·설계 수정은 expected_revision 검사로 동시 편집 충돌을 감지한다.

## 접근 권한

| 행위 | viewer | editor | owner |
| --- | --- | --- | --- |
| 프로젝트 결과 조회 | 가능 | 가능 | 가능 |
| 실험·설계·노트 작성 | 불가 | 가능 | 가능 |
| 결과 확정·baseline 선정 | 불가 | 가능 | 가능 |
| 구성원·등록 권한 관리 | 불가 | 불가 | 가능 |

로그인과 프로젝트 접근 권한을 분리한다. 모든 연구 테이블에 RLS를 적용하고 비회원 조회를 차단한다.
복합 변경은 actor와 project 권한을 검사하는 RPC로 제한한다. 직접 테이블 변경 권한은 최소화한다.
마지막 owner를 제거하거나 강등하지 못하게 한다.

SECURITY DEFINER 함수는 고정 search_path, 최소 grants, 명시적인 권한 검사를 사용한다.
등록 전용 권한은 조회·삭제·수정 권한과 분리하고 관리 권한의 키를 브라우저에 노출하지 않는다.
인증 정보는 해시로 보관하고 원문을 로그에 남기지 않는다.

## API 규약

기능 구현 시 버전이 명시된 입력 규약을 정의한다.
등록 요청은 기존 실험·설계 버전·비교 조건을 명확히 참조하고, 단위·지표 버전을 검증한다.

- 같은 등록 ID와 같은 정규화 내용이면 중복 성공으로 응답한다.
- 같은 ID에 다른 내용이 들어오면 409 충돌로 처리한다.
- 결과와 지표는 하나의 transaction으로 저장한 뒤 성공 응답을 반환한다.
- 권한 오류, 형식 오류, 등록 충돌과 일시적 장애를 구분한다.
- 사용자 입력의 작성자·프로젝트 값을 그대로 신뢰하지 않는다.
- 오류 응답으로 다른 프로젝트의 존재 여부나 내용을 노출하지 않는다.

스키마 검증 전후의 제한, 유한한 수치 검사, 입력 크기 제한을 적용한다.
브라우저에서 받은 Markdown은 raw HTML을 비활성화하거나 정제한다.

## 집계와 조회

확정 selection을 기준으로 지표별 평균, 표본 표준편차와 표본 수를 계산한다.
결측·실패는 제외 이유와 함께 보존하고 0으로 대체하지 않는다.
표본이 하나면 표준편차를 null로 표시한다.

지표별 단위·개선 방향·평가 버전을 유지한다. 비교 조건이 다르면 delta나 순위를 계산하지 않는다.
baseline이 0이면 상대 변화율을 계산하지 않는다. 대응 관계가 확인되지 않으면 paired 분석을 제공하지 않는다.

목록 조회에는 project_id와 정렬 열의 복합 인덱스 및 cursor pagination을 사용한다.
전체 JSON의 인덱스나 영구 집계 테이블은 필요성이 확인된 뒤 도입한다.

## 구현 검증

- 비회원·다른 프로젝트 접근 및 권한 승격 차단
- 중복·충돌 등록과 동시 등록 경합
- 지표 오류 시 전체 transaction rollback
- 결과 확정 후 변경 차단과 과거 baseline 보존
- 동시 노트 수정 충돌
- 결측·실패·단일 표본·baseline=0 집계
- 백업 복원 후 실험·노트·권한 관계 보존

migration을 DB 구조의 원본으로 삼고, 실제 스키마에서 생성한 타입을 프론트에 반영한다.
